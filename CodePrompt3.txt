## 2. PHASE 3 OBJECTIVE

Implement an intelligent complaint-processing system with four major capabilities:

1. AI-assisted complaint category suggestions.
2. Image-based similarity detection.
3. Location-based duplicate detection.
4. Text-based complaint similarity detection.

Example:

Citizen A submits:

"Garbage has accumulated near the main entrance of ABC Colony."

Citizen B submits:

"There is a huge garbage pile near ABC Colony main gate."

These may represent the same civic issue.

CivicX should identify the possibility of a duplicate and show the related complaint to the admin.

Important:

Duplicate detection must not automatically reject a complaint.

The administrator must make the final decision.

## 5. IMAGE SIMILARITY DETECTION

Implement image-based duplicate detection.

First inspect the existing image-hash schema.

Recommended approach:

A. Cryptographic hash:
- SHA-256.
- Detect exact duplicate files.

B. Perceptual hash:
- Implement pHash or an equivalent perceptual hashing algorithm.
- Detect resized or slightly modified copies of an image.

C. Store:
- Image ID.
- Complaint ID.
- Hash algorithm.
- Hash value.
- Creation timestamp.

Requirements:

- Generate hashes after successful image upload.
- Do not trust hashes provided by clients.
- Compare against existing eligible complaint images.
- Use a configurable similarity threshold.
- Handle multiple images per complaint.
- Avoid treating exact duplicate image uploads as proof that two reports describe the same real-world incident.

If an image-processing library is required, justify and document the dependency.

Do not implement fake image recognition.

## 6. LOCATION-BASED DUPLICATE DETECTION

Use GPS coordinates from the complaint.

Implement configurable geographic matching.

Example configuration:

civicx.duplicate.location-radius-meters=100

This is an initial configurable value, not a universal rule.

Requirements:

- Compare new complaints with nearby existing complaints.
- Use a proper geographic distance calculation.
- Exclude complaints with missing or invalid coordinates.
- Filter out inappropriate statuses where necessary.
- Consider complaint category compatibility.
- Do not compare coordinates using simplistic string equality.
- Avoid inefficient full-table scans.

Return:
- Matching complaint reference.
- Distance in meters.
- Matching category.
- Current status.
- Similarity explanation.

Use indexed queries and bounding-box filtering before precise distance calculation.

## 8. COMBINED DUPLICATE DETECTION ENGINE

Create a service:

- Location similarity.

- Category compatibility.

Produce a structured result.

## 10. ASYNCHRONOUS PROCESSING

Avoid making complaint submission slow because of image hashing or duplicate detection.

Use the existing RabbitMQ infrastructure if suitable.

Suggested workflow:

1. Citizen submits complaint.
2. Complaint is saved in MySQL.
3. An event is published after successful database persistence.
4. Background consumer performs classification and duplicate detection.
5. Results are saved in MySQL.
6. Admin can view the results.

Important reliability requirements:

- Handle consumer failures.
- Add retry policies.
- Avoid processing the same event multiple times.
- Consider a transactional outbox if required for reliable event publishing.
- Do not lose events when database persistence succeeds but message publishing fails.
- Provide a way to retry failed AI processing.

If RabbitMQ is unavailable, complaint submission should still work.
