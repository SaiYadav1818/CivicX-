# PROMPT 12 — CivicX Local Workers, Job Availability & On-Demand Services

You are a senior full-stack engineer working on my existing CivicX project.

Implement a new independent module called **CivicX Local Workers & Services**.

First inspect the actual repository, backend, frontend, database, authentication, authorization, locality system, notifications and existing modules.

Do not assume the existing implementation. Reuse existing infrastructure and follow existing coding conventions.

## 1. Product Vision

CivicX should help local residents find nearby workers and service providers.

Many local workers are available for work but do not have an easy way to tell nearby residents that they are free.

For example:
- A plumber is free today from 2 PM to 7 PM.
- An electrician is available tomorrow.
- An auto driver is available for local trips.
- Construction labourers are looking for work.
- A carpenter is available for furniture repairs.
- A painter is available for house painting.

Workers should be able to publish their availability. Residents should be able to discover workers in their locality and contact them directly.

The platform should support both:
1. Workers announcing their availability.
2. Residents posting a request when they need a worker.

## 3. Worker Registration

Allow workers to register using the existing CivicX authentication system.

Worker profile fields:

- Worker name
- Profile photo
- Mobile number
- Optional email
- Primary profession
- Additional skills
- Experience
- Languages spoken
- Locality
- Service areas
- Short description
- Optional expected rate
- Available work types
- Verification status

Allow individual workers and registered local service businesses.

A worker should be able to register independently without needing a company.

Verification statuses:
- PENDING
- VERIFIED
- REJECTED
- SUSPENDED

Do not display a verified badge unless verification is actually completed.

## 4. Worker Availability Posting

This is the most important functionality.

Workers should be able to publish availability announcements.

Example:

Name: Ramesh

Profession: Plumber

Locality: Street 9

Availability date: November 6

Available from: 2 PM

Available until: 7 PM

Work accepted:
- Tap repair
- Pipe leakage
- Bathroom plumbing
- Water connection repair

Expected charge: Contact for price.

Announcement:

"Available for plumbing work in Street 9 and nearby areas today from 2 PM to 7 PM."

Workers should be able to:
- Publish availability.
- Edit availability.
- Change availability timings.
- Mark themselves busy.
- Mark themselves unavailable.
- Cancel an announcement.
- Publish availability for another day.
- Set recurring availability if desired.

Availability statuses:
- AVAILABLE
- BUSY
- UNAVAILABLE
- EXPIRED

Every availability announcement must have a date and time range.

Automatically expire old announcements.

Never display an expired announcement as current availability.

## 5. Customer Discovery

Create a separate Local Workers section in CivicX.

Residents should be able to:

1. Select their locality.
2. Browse available workers.
3. Search by profession.
4. Filter by nearby locality.
5. Filter by availability date.
6. Filter by time.
7. View worker profiles.
8. View experience and skills.
9. View expected charges if provided.
10. Call or message a worker.

Example:

A customer needs a plumber.

They open CivicX and select:
- Category: Plumber
- Locality: Street 9
- Date: Today
- Time: 4 PM

CivicX displays workers who have matching availability.

Show:
- Worker name
- Profession
- Profile photo
- Locality
- Available time
- Skills
- Experience
- Expected price, if provided
- Verification status

Do not display workers who are unavailable or whose announcements have expired.

## 6. Call and Message Functionality

Users should be able to contact workers.

Provide:
- Call button.
- WhatsApp contact option where supported.
- In-app messaging as a future-ready feature.

For direct contact:
- Show the contact number only when the user intentionally selects the contact option and the worker has consented.
- Never expose phone numbers in public API responses or public listings.
- Apply appropriate abuse prevention and rate limiting.

If in-app chat already exists, reuse it. Otherwise, do not introduce an unnecessarily complicated messaging system in this phase.

## 7. Customer Job Request

Allow residents to post a request when they cannot find an available worker.

Example:

"I need a plumber for a water leakage problem at my house in Street 9 tomorrow morning."

Request details:
- Required profession
- Description of work
- Optional images
- Locality
- Preferred date
- Preferred time
- Expected budget (optional)

Matching workers in the selected service area should be able to discover the request.

Workers can respond:
- I am available.
- I am interested.
- Contact me.
- I can do this work for an estimated price.

The customer can contact a suitable worker.

Do not automatically assign a worker without the customer's confirmation.

Do not force every profession into the same workflow.

### A. Plumber and Electrician

- Service area

### D. Carpenters and Painters

- Estimated charges

### E. Household Services
Support:
- Service category
- Availability
- Service area
- One-time or recurring service
- Estimated charges

Keep profession-specific information configurable.

## 9. Availability and Booking Workflow

Initially support direct contact and optional appointment confirmation.

Suggested workflow:

- AVAILABLE
- CUSTOMER_INTERESTED
- CONTACTED
- APPOINTMENT_REQUESTED
- APPOINTMENT_CONFIRMED
- WORK_STARTED
- WORK_COMPLETED
- CANCELLED

Do not force users to make a booking through CivicX when they only want to call a worker.

The platform should support discovery and direct contact even without an in-app booking.

For bookings, both customer and worker should be able to see the confirmed appointment details.

Prevent duplicate or conflicting confirmed appointments where appointment booking is enabled.

- Appointment requests.

## 14. Privacy and Safety

This module involves direct interaction between residents and workers.

Implement:

- Phone number privacy.
- Optional public profile visibility.
- Consent before revealing contact information.
- Report and block functionality.
- Admin verification.
- Abuse prevention.
- Rate limiting.
- Safe handling of profile photos and documents.
- Approximate location in public listings.
- No public display of home addresses.
- No continuous location tracking.

For jobs at private residences, share the full service address only through a controlled customer-worker interaction after the customer chooses to contact or book the worker.

Do not claim that every worker is background-checked unless that process actually exists.

## 16. API Design

Adapt endpoints to the actual project conventions.

Worker:
- POST /api/v1/local-workers/register
- GET /api/v1/local-workers/my-profile
- PUT /api/v1/local-workers/my-profile
- POST /api/v1/local-workers/availability
- GET /api/v1/local-workers/my-availability
- PATCH /api/v1/local-workers/availability/{id}

- POST /api/v1/local-workers/job-requests

Worker responses:
- GET /api/v1/local-workers/job-requests/nearby

Appointments:
- POST /api/v1/local-workers/appointments
- GET /api/v1/local-workers/appointments
- PATCH /api/v1/local-workers/appointments/{appointmentId}/status

Admin:
- GET /api/v1/admin/local-workers
- PATCH /api/v1/admin/local-workers/{workerId}/verify
- PATCH /api/v1/admin/local-workers/{workerId}/suspend

Document all implemented APIs in Swagger/OpenAPI.
