## 2. PHASE 2 OBJECTIVE

Implement a complete citizen complaint submission and management workflow.

A citizen should be able to:

1. Log in.
2. Report a civic issue.
3. Select a complaint category.
4. Enter a description.
5. Upload complaint photographs.
6. Provide GPS coordinates.
7. Submit the complaint.
8. Receive a unique CivicX complaint ID.
9. View their submitted complaints.
10. View individual complaint details and status.

An administrator should be able to:

1. View submitted complaints.
2. Review complaint details and photographs.
3. Verify or reject complaints.
4. Add an internal review note.
5. Update complaint status according to permitted workflow.
6. View complaint history.

## 4. CITIZEN COMPLAINT SUBMISSION

Implement:

POST /api/v1/complaints

Authentication: Required.

Role: CITIZEN.

Request should support:

- Category ID
- Complaint title
- Description
- Latitude
- Longitude
- Address
- Landmark
- Ward ID, if available
- Zone ID, if available
- Photo attachment references

Validation:

- Category must exist and be active.
- Title and description must not be blank.
- Description must have a reasonable maximum length.
- Latitude must be between -90 and 90.
- Longitude must be between -180 and 180.
- Validate all referenced IDs.
- Reject invalid or missing mandatory information.
- Do not trust citizen-provided user IDs. Obtain the citizen identity from the authenticated JWT principal.

Generate a unique complaint reference:

CX-000001

Use a concurrency-safe generation strategy. Do not rely on an unsafe count-based approach.

The complaint must record:
- Citizen ID
- Creation timestamp
- Initial status
- Location
- Category
- Description
- Reference number

## 5. IMAGE UPLOAD

Implement secure complaint image upload.

Endpoint:

POST /api/v1/complaints/{complaintId}/images

Requirements:

- Accept JPEG, PNG and WebP.
- Validate actual file content, not just filename or MIME type.
- Configure maximum file size.
- Allow a reasonable maximum number of images per complaint.
- Generate random storage filenames.
- Prevent path traversal.
- Reject executable files and unsupported formats.
- Do not expose filesystem paths publicly.
- Save image metadata in the database.
- Store original filenames only as sanitized metadata.
- Ensure users can upload images only to complaints they own.
- Admin and supervisor access must follow RBAC.

Storage architecture:

Create an abstraction such as:

ComplaintFileStorageService

Implement local storage for development.

Keep the design ready for S3-compatible object storage in a future phase.

Do not claim S3 integration unless it is actually implemented and tested.

Provide secure image retrieval through an authenticated endpoint or controlled access mechanism.

## 7. COMPLAINT STATUS WORKFLOW

Implement a controlled workflow.

Suggested statuses:

SUBMITTED
UNDER_REVIEW
VERIFIED
REJECTED
ASSIGNED
IN_PROGRESS
RESOLVED
CLOSED
REOPENED

Important:

- A citizen must not be able to mark their own complaint VERIFIED or RESOLVED.
- Only authorized roles may perform administrative transitions.
- Invalid status transitions must return HTTP 409 or another appropriate conflict response.
- Rejection must require a reason.
- Every status change must record who changed it and when.
- Store status history.
- Do not overwrite history when status changes.

Keep the workflow extensible for department assignment in a later phase.
