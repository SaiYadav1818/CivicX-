# PROMPT 10 — CivicX Local Shops & Local Delivery Module

You are a senior full-stack engineer working on my existing **CivicX** project.

Your task is to inspect the actual repository and implement a new module called **CivicX Local Shops**.

Do not assume anything about the existing code. First inspect the project architecture, database, authentication, APIs, frontend, existing modules, and development conventions.

## 1. Product Vision

CivicX should help people discover shops and businesses in their own local areas.

For example, a person living in Street 9 should be able to open CivicX, select Local Shops, and discover nearby:

- Grocery stores and supermarkets
- Restaurants and hotels
- Bakeries
- Vegetable and fruit shops
- Medical stores
- Tiffin centres
- Meat and chicken shops
- Tea and snacks shops
- Clothing stores
- Other local businesses

Shop owners should be able to register their shops, manage their business information, update availability, and eventually accept local orders.

Customers should be able to discover shops, check whether they are open, browse products, and order from nearby shops.

This must be a separate business module within CivicX.

## 2. Architecture Requirements

Before implementing:

1. Inspect the existing backend and frontend structure.
2. Identify the existing authentication and role-based access control.
3. Inspect the existing database schema and Flyway migration history.
4. Identify existing locality, ward, zone, and address structures.
5. Identify existing image/file upload infrastructure.
6. Inspect existing API response formats and error-handling conventions.
7. Identify the existing admin dashboard architecture.

Reuse existing shared infrastructure wherever appropriate.

Important:
- Do not create another authentication system.
- Do not duplicate existing user or locality tables.
- Do not modify existing modules unnecessarily.
- Do not break existing APIs.
- Do not modify previously applied Flyway migrations.
- Create new migrations for all new database changes.
- Follow the existing project's coding standards.

If an existing feature already provides the required functionality, reuse it instead of creating a duplicate.

## 3. Shop Owner Registration

Create a shop owner registration workflow.

A shop owner should be able to submit:

- Shop name
- Owner name
- Mobile number
- Email address (optional if supported)
- Shop description
- Shop category
- Shop address
- Locality
- Street name or number
- Ward/zone, if supported by the existing system
- Shop location or map coordinates
- Shop opening time
- Shop closing time
- Shop photos
- Business documents, if required by admin policy

Shop registration must go through admin verification.

Shop statuses:

- PENDING_APPROVAL
- APPROVED
- REJECTED
- SUSPENDED

Only approved shops should appear in the public Local Shops directory.

A shop owner must only manage shops they own or are authorized to manage.

## 4. Local Shops Discovery — Customer Side

Create a separate Local Shops section in the CivicX application.

Users should be able to:

1. Select their locality.
2. View shops in that locality.
3. Browse shops in nearby localities.
4. Search by shop name.
5. Filter by shop category.
6. Filter by Open or Closed status.
7. View shop distance where reliable location data is available.
8. Open a shop profile.
9. View shop contact details and business hours.

Example:

A user selects Street 9.

CivicX displays:

- Sai Grocery Store
- Sri Lakshmi Bakery
- Local Vegetable Shop
- Fresh Chicken Centre
- Sai Tiffin Centre

Do not show unapproved or suspended shops.

Do not expose private owner information.

Location permission must be optional. Users should also be able to select a locality manually.

## 5. Shop Open / Closed Controls

This is an important feature.

The shop owner must have a simple ON/OFF control to update shop availability.

Example:

Shop availability: ON = OPEN

Shop availability: OFF = CLOSED

The shop owner dashboard should display:

- Shop Open/Closed toggle
- Accept Orders toggle
- Delivery Available toggle
- Pickup Available toggle

When the owner changes the shop status, customers should see the updated status.

Important business rules:

1. Only authorized shop owners can change their shop status.
2. A closed shop must not accept new orders.
3. A shop can be open but temporarily stop accepting orders.
4. A shop can be open but have delivery disabled.
5. A shop can offer pickup without delivery.
6. Admin can suspend a shop regardless of owner availability settings.
7. A suspended shop must not appear as an active shop.
8. Record status changes with timestamps and the responsible user.

Do not rely only on frontend controls. Validate every status change on the backend.

### Stale status handling

If a shop owner has not updated the shop availability for a configured period, show:

"Status not recently updated"

Do not automatically promise customers that a shop is open based only on its usual opening hours.

Opening hours and live availability must be treated as separate information.

## 6. Shop Profile

Every approved shop should have its own public profile.

Display:

- Shop name
- Shop image
- Description
- Category
- Address
- Locality
- Opening hours
- Current availability
- Delivery availability
- Pickup availability
- Contact information
- Product catalogue
- Available offers, if implemented

The profile must clearly distinguish:

- Open
- Closed
- Temporarily not accepting orders
- Delivery unavailable
- Pickup unavailable
- Status not recently updated

## 7. Product Catalogue

Allow approved shop owners to manage their products.

Each product should support:

- Product name
- Product description
- Product category
- Product image
- Selling price
- Unit (kg, gram, litre, piece, packet, etc.)
- Product availability
- Optional discount price
- Active/inactive status

Examples:

Grocery:
- Rice — ₹60/kg
- Sugar — ₹45/kg
- Cooking Oil — ₹150/litre

Bakery:
- Cake — ₹350
- Bread — ₹40
- Biscuits — ₹30

Prices above are examples only.

Shop owners should be able to:

- Add products
- Edit products
- Delete or deactivate products
- Change prices
- Mark products as out of stock
- Upload product images

Customers must not be able to modify shop products or prices.

Validate prices and product information on the backend.

## 8. Local Ordering System — Prepare the Architecture

Design the ordering system so that CivicX can support local purchases.

Customer flow:

1. Customer opens Local Shops.
2. Selects a locality.
3. Opens a shop.
4. Views products and prices.
5. Adds products to cart.
6. Selects delivery or pickup.
7. Enters or selects a delivery address.
8. Reviews the order summary.
9. Places the order.
10. Shop owner receives the order.
11. Shop owner accepts or rejects it.
12. Customer can track order status.

Order statuses:

- PLACED
- ACCEPTED
- REJECTED
- PREPARING
- READY_FOR_PICKUP
- OUT_FOR_DELIVERY
- DELIVERED
- CANCELLED

Important rules:

- A customer cannot order from a closed shop.
- A customer cannot order unavailable products.
- A shop cannot accept orders when Accept Orders is OFF.
- A shop cannot accept delivery orders when Delivery Available is OFF.
- Product prices must be validated using backend data.
- Store the product name, quantity and price as an order-item snapshot.
- Do not trust totals or prices sent by the frontend.
- Prevent unauthorized access to another customer's orders.
- Prevent a shop owner from accessing orders belonging to another shop.
- Support order cancellation according to defined business rules.
- Keep an order status history.

For the first implementation, prepare the architecture and implement the core ordering flow only if it can be done safely within this phase.

Do not integrate a real payment gateway without a separate implementation and security review.

## 9. Local Delivery

CivicX should initially support delivery within the shop's local service area.

For example:

Sai Grocery Store:
- Delivery enabled
- Delivery radius: 3 km
- Minimum order: configurable
- Delivery charge: configurable

Shop owners should be able to configure:

- Delivery ON/OFF
- Pickup ON/OFF
- Service radius or selected localities
- Minimum order amount
- Delivery charge

Validate whether the customer's delivery address is within the shop's supported delivery area.

Do not claim that a delivery is available if the location cannot be validated.

### Delivery partner support — Future-ready

Keep the architecture extensible for future delivery partners.

Do not build a complicated delivery partner application in this phase.

For now, support shop-managed delivery and pickup.

Future possibilities:
- Delivery partner registration
- Delivery assignment
- Delivery partner availability
- Delivery tracking
- Delivery earnings

## 13. API Design

Follow existing API conventions.

Proposed API groups:

Shop owner:
- POST /api/v1/local-shops
- GET /api/v1/local-shops/my-shops
- PUT /api/v1/local-shops/{shopId}
- PATCH /api/v1/local-shops/{shopId}/availability
- PATCH /api/v1/local-shops/{shopId}/accept-orders
- PATCH /api/v1/local-shops/{shopId}/delivery-settings

Customer:
- GET /api/v1/local-shops
- GET /api/v1/local-shops/{shopId}
- GET /api/v1/local-shops/{shopId}/products
- GET /api/v1/local-shops/categories
- GET /api/v1/local-shops/nearby

Products:
- POST /api/v1/local-shops/{shopId}/products
- PUT /api/v1/local-shops/{shopId}/products/{productId}
- DELETE /api/v1/local-shops/{shopId}/products/{productId}

Orders:
- POST /api/v1/local-orders
- GET /api/v1/local-orders/my-orders
- GET /api/v1/local-orders/{orderId}
- GET /api/v1/local-shops/{shopId}/orders
- PATCH /api/v1/local-orders/{orderId}/status

Admin:
- GET /api/v1/admin/local-shops
- PATCH /api/v1/admin/local-shops/{shopId}/approve
- PATCH /api/v1/admin/local-shops/{shopId}/reject
- PATCH /api/v1/admin/local-shops/{shopId}/suspend

These are suggested endpoints. Adapt them to the actual project architecture.

Document every implemented endpoint in Swagger/OpenAPI.
